# Документация по архитектуре Miyu

## 1. Обзор проекта

Miyu — это музыкальный стриминговый сервис с веб-интерфейсом, backend API, SQLite-базой данных и отдельным AI-сервисом для анализа контента и рекомендаций.

Архитектура проекта разделена на 3 основные части:

- **Frontend** — клиентское приложение для пользователей, артистов, модераторов и администраторов.
- **Backend** — REST API, бизнес-логика, аутентификация, работа с БД и файлами.
- **AI-service** — отдельный Python-сервис для анализа треков, модерации и рекомендательных функций.

## 2. Backend

### 2.1. Технологический стек backend

Основной backend расположен в директории `backend/`.

**Языки программирования:**

- **TypeScript** — основной язык backend-части.
- **SQL** — описание схемы базы данных и миграций.

**Фреймворки и библиотеки:**

- **Node.js** — серверная runtime-среда.
- **Express 5** — HTTP-сервер и маршрутизация API.
- **sqlite3** — драйвер для работы с SQLite.
- **cors** — поддержка cross-origin запросов.
- **dotenv** — загрузка переменных окружения.
- **jsonwebtoken** — JWT-аутентификация.
- **bcryptjs** — хеширование паролей.
- **multer** — загрузка файлов.
- **qrcode** — генерация QR-кодов для билетов и связанных сценариев.
- **ts-node / TypeScript** — разработка и сборка backend-кода.

### 2.2. Организация backend

Ключевые директории backend:

- `backend/index.ts` — точка входа приложения.
- `backend/routes/` — REST-маршруты.
- `backend/db/` — подключение к базе и миграции.
- `backend/middleware/` — middleware, в том числе авторизация.
- `backend/services/` — интеграции, например с AI-service.
- `uploads/` — загружаемые пользователями файлы: треки, видео, обложки, превью.

### 2.3. Основные API-модули

В backend зарегистрировано большое количество доменных роутов:

- `auth` — регистрация, логин, токены.
- `user` — профиль и пользовательские настройки.
- `admin` — административные функции.
- `artist`, `artist-albums`, `artist-videos` — кабинеты и контент артистов.
- `album`, `track`, `videos` — музыкальный и видеоконтент.
- `moderation` — модерация контента.
- `likes`, `playlists`, `history` — пользовательская библиотека.
- `friendships`, `following`, `notifications` — социальные функции.
- `concerts`, `transactions` — концерты, билеты, платежи.
- `achievements`, `user-achievements`, `admin-achievements` — система достижений.
- `search` — поиск.
- `support` — обращения в поддержку.
- `ai` — AI-функции анализа.
- `recsys` — рекомендации и персонализированная выдача.
- `home` — данные для главной страницы.

### 2.4. Работа с БД

Backend использует **SQLite** как основную базу данных.

Подключение организовано через `backend/db/index.ts`:

- база открывается через `sqlite3.Database`;
- включается `PRAGMA foreign_keys = ON`;
- реализованы утилиты:
  - `runQuery()` — выполнение SQL-запросов;
  - `getOne()` — получение одной записи;
  - `getAll()` — получение списка записей.

### 2.5. Миграции

В проекте есть два уровня эволюции схемы:

1. **Базовая схема** — `database/schema.sql`.
2. **Прикладные миграции** — `backend/db/migrate.ts` и SQL-файлы в `database/migrations/`.

Миграции в `migrate.ts` дополняют схему новыми таблицами и колонками, например:

- `artist_applications`
- `support_tickets`
- цветовые поля пользователя: `palette_mode`, `palette_primary`, `palette_secondary`, `palette_tertiary`
- расширение `track_analysis`
- `track_similarity`
- `user_taste_profile`
- `recsys_feedback`
- `personalized_home_cache`
- `personalized_home_playlists`
- `ai_jobs`

Это говорит о том, что БД развивается итеративно без тяжелой ORM-абстракции: схема поддерживается вручную SQL и TypeScript-миграциями.

## 3. Строение базы данных

### 3.1. Общая модель данных

БД построена вокруг музыкальной платформы с несколькими подсистемами:

- пользователи и роли;
- артисты и музыкальный каталог;
- воспроизведения и аналитика;
- видео и клипы;
- плейлисты и лайки;
- социальное взаимодействие;
- достижения и геймификация;
- модерация;
- концерты, билеты и платежи;
- AI-анализ и рекомендации.

### 3.2. Основные сущности

#### Пользователи

- `users` — базовая таблица аккаунтов.
- `artist_profiles` — профиль артиста, привязанный к `users`.
- `refresh_tokens` — refresh-токены для авторизации.

Роли пользователя задаются через поле `role`:

- `user`
- `artist`
- `moderator`
- `admin`

#### Музыкальный каталог

- `albums` — альбомы, синглы, EP.
- `tracks` — треки.
- `track_plays` — история воспроизведений треков.
- `videos` — видеоконтент и клипы.
- `video_views` — история просмотров видео.

Связи:

- один артист (`users`) → много альбомов (`albums`);
- один артист (`users`) → много треков (`tracks`);
- один альбом (`albums`) → много треков (`tracks`);
- видео может ссылаться на артиста, альбом и конкретный трек.

#### Плейлисты и лайки

- `playlists`
- `playlist_tracks`
- `playlist_likes`
- `likes` — лайки треков.
- `album_likes` — лайки альбомов.
- `artist_follows` — подписки на артистов.

#### Социальный контур

- `friendships` — дружба и статусы заявок.
- `notifications` — уведомления.
- `now_playing` — текущий прослушиваемый трек.

#### Аналитика и AI

- `user_stats` — пользовательская статистика по дням.
- `track_analysis` — результаты AI-анализа треков.
- `track_similarity` — похожесть треков.
- `user_taste_profile` — профиль музыкального вкуса пользователя.
- `recsys_feedback` — сигналы обратной связи для рекомендаций.
- `personalized_home_cache` — кеш персонализированной главной страницы.
- `personalized_home_playlists` — персональные подборки.
- `ai_jobs` — задания AI-анализа.

#### Достижения и геймификация

- `achievements`
- `user_achievements`
- `achievement_showcase`

#### Модерация и безопасность

- `moderation_queue`
- `reports`
- `artist_applications`
- `support_tickets`

#### Концерты и монетизация

- `concerts`
- `ticket_types`
- `tickets`
- `subscriptions`
- `transactions`
- `donations`
- `promotions`

### 3.3. Особенности схемы БД

Особенности реализации:

- активно используются **foreign key** связи с `ON DELETE CASCADE`;
- статусы задаются через **CHECK constraints**;
- для производительности созданы индексы по основным полям:
  - артистам,
  - пользователям,
  - статусам,
  - воспроизведениям,
  - транзакциям,
  - модерации;
- присутствует `VIEW user_top_tracks` для сценариев рекомендаций;
- в `track_analysis` и смежных AI-таблицах используются текстовые, числовые и бинарные поля, включая эмбеддинги и JSON-данные.

### 3.4. Логическая схема доменов

Упрощенно структуру БД можно представить так:

1. **Accounts domain**
   - users
   - refresh_tokens
   - artist_profiles

2. **Content domain**
   - albums
   - tracks
   - videos

3. **Consumption domain**
   - track_plays
   - video_views
   - now_playing
   - user_stats

4. **Library & social domain**
   - playlists
   - playlist_tracks
   - likes / album_likes / playlist_likes
   - friendships
   - notifications
   - artist_follows

5. **Commerce domain**
   - concerts
   - ticket_types
   - tickets
   - subscriptions
   - transactions
   - donations
   - promotions

6. **AI & moderation domain**
   - track_analysis
   - track_similarity
   - user_taste_profile
   - recsys_feedback
   - moderation_queue
   - reports
   - ai_jobs

## 4. AI-service

AI-сервис расположен в директории `ai-service/` и работает отдельно от основного backend.

### 4.1. Стек AI-service

**Язык:**

- **Python 3.11**

**Фреймворки и библиотеки:**

- **FastAPI** — HTTP API AI-сервиса.
- **Uvicorn** — запуск ASGI-приложения.
- **Pydantic / pydantic-settings** — конфигурация и модели данных.
- **Redis** — очередь и кеш.
- **RQ** — фоновые задания.
- **NumPy / SciPy** — численные вычисления.
- **librosa / soundfile / audioread** — аудиоанализ.
- **torch / torchaudio / panns-inference** — аудиоэмбеддинги и теги.
- **faster-whisper** — транскрипция текста песен.
- **sentence-transformers / transformers** — текстовые эмбеддинги.
- **detoxify** — токсичность и текстовая модерация.
- **pyacoustid** — аудиофингерпринты.
- **hnswlib** — ANN-индекс для поиска похожих объектов.
- **implicit / scikit-learn** — рекомендательные алгоритмы.
- **Pillow / opennsfw2** — модерация изображений.
- **SQLAlchemy / aiosqlite** — работа с данными и асинхронными сценариями.
- **prometheus-client / loguru** — метрики и логирование.

### 4.2. Назначение AI-service

AI-service отвечает за:

- анализ треков;
- извлечение аудио-признаков;
- транскрипцию текста;
- модерацию текста и изображений;
- построение схожести треков;
- персонализированные рекомендации;
- построение профиля музыкального вкуса пользователя.

### 4.3. Интеграция backend ↔ AI-service

Интеграция реализована двумя способами:

1. **Прямые HTTP-вызовы** к AI-service.
2. **Постановка задач в очередь** через backend-сервис `backend/services/aiService.ts`.

Backend использует переменную `AI_SERVICE_URL` и умеет:

- ставить задачу `analyze_track` после загрузки трека;
- проксировать запросы рекомендаций через `backend/routes/recsys.ts`;
- отдавать пользователю похожие треки, фид, rebuild профиля, статистику индексов.

## 6. Дизайнерские решения frontend

### 6.1. Общая визуальная концепция

Интерфейс построен в стилистике:

- **dark UI**;
- **glassmorphism**;
- **neon / cosmic accents**;
- **music-first визуализация**.

Визуально продукт напоминает современный музыкальный сервис с упором на атмосферу ночного, космического, эмоционального цифрового пространства.

### 6.2. Ключевые дизайнерские принципы

1. **Темная базовая сцена**
   - фон почти черный: `#050505`, `#0a0a0f`;
   - светлый текст на темном фоне для высокой контрастности.

2. **Стеклянные панели**
   - используются классы `glass`, `glass-hover`, `glass-accent`, `glass-edge`;
   - применяется `backdrop-filter: blur(...)` и полупрозрачные слои;
   - создается эффект парящих карточек и оверлеев.

3. **Градиентные акценты**
   - широко используются градиенты в карточках, баннерах, профилях, жанрах и CTA-блоках;
   - основные переходы — между фиолетовым, розовым, синим, оранжевым, бирюзовым.

4. **Музыкальная динамика**
   - интерфейс не статичен: анимации баров, обложек, всплывающих окон и плеера делают продукт более «живым».

5. **Персонализация внешнего вида**
   - поддерживается автоматическая и кастомная палитра пользователя;
   - палитра может сохраняться локально и на сервере.

### 6.3. Цветовая палитра

#### Базовые цвета

Из `frontend/src/index.css` и `tailwind.config.js` можно выделить основную палитру:

- **Primary blue:** `#0ea5e9`
- **Background black:** `#050505`
- **Background gradient dark:** `#0a0a0f`
- **Secondary dark slate:** `#1e293b`
- **Main text:** `#f8fafc`
- **Secondary text:** `#94a3b8`

#### Главный фирменный градиент

- **Purple:** `#8B5CF6`
- **Pink:** `#EC4899`

Градиент:

- `linear-gradient(135deg, #8B5CF6 0%, #EC4899 100%)`

Этот градиент используется как один из основных визуальных маркеров бренда.

#### Дополнительные акцентные цвета

В системе пользовательских и автоматических палитр также используются:

- `#3B82F6`
- `#F59E0B`
- `#EF4444`
- `#10B981`
- `#06B6D4`
- `#F97316`
- `#6366F1`
- `#14B8A6`
- `#F43F5E`
- `#84CC16`
- `#22C55E`

#### Tailwind-палитры

Собственные расширения темы:

- **primary 50–950** — шкала голубого/синего акцента;
- **dark 50–950** — шкала темных slate-оттенков.

### 6.4. Персонализация цвета

В `ThemeContext.tsx` реализована логика пользовательских тем:

- режим `auto` — палитра генерируется по имени пользователя;
- режим `custom` — пользователь задает `primary`, `secondary`, `tertiary`;
- значения хранятся в `localStorage` и могут сохраняться на backend через `PATCH /api/user/me`.

Это важное UX-решение: интерфейс становится персонализированным и эмоционально привязанным к аккаунту.

## 8. Вывод по архитектуре

### Сильные стороны текущего решения

1. **Четкое разделение ответственности**
   - frontend, backend и AI-service вынесены в отдельные контуры.

2. **Простая и понятная backend-архитектура**
   - Express + SQLite позволяет быстро развивать продукт и легко отлаживать его локально.

3. **Богатая предметная модель БД**
   - схема покрывает музыку, социальные связи, аналитику, рекомендации, монетизацию и модерацию.

4. **Сильный визуальный стиль frontend**
   - темная тема, glassmorphism, космические эффекты и персональные палитры делают интерфейс узнаваемым.

5. **Наличие AI-контура**
   - отдельный Python-сервис под анализ и recsys делает архитектуру более масштабируемой.

### Потенциальные направления развития

1. Перевод части ручных SQL-миграций в более формализованный migration-процесс.
2. Выделение архитектурной схемы БД в отдельную ER-диаграмму.
3. Документирование API в формате OpenAPI/Swagger для backend.
4. Описание дизайн-системы frontend в виде отдельного UI-guideline.
5. Формализация контрактов между backend и AI-service.
